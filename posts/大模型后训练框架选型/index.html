大模型后训练框架选型：从 TRL 到 verl、OpenRLHF 与 NeMo RL

发表于2026-08-28|更新于2026-08-28|模型训练

前面几篇文章介绍了 SFT、DPO、PPO、GRPO 和 OPD 的原理。但真正打开服务器准备训练时，问题会迅速从“损失函数是什么”变成：数据该写成什么格式？模型如何分布到多张卡？谁负责批量生成回答？奖励函数在哪里执行？训练中的新参数又怎样同步给推理引擎？

好消息是，我们通常不需要从零实现这些环节。目前比较成熟的后训练框架，大致可以分为三类：

  • 通用微调工具箱：TRL、LLaMA-Factory、Axolotl、ms-swift，适合快速完成 SFT、DPO 和中小规模 GRPO；
  • 规模化在线强化学习框架：OpenRLHF、verl、NeMo RL，重点解决 PPO、GRPO、OPD 的多模型、多节点和高吞吐问题；
  • 底层执行组件：Transformers、PEFT、DeepSpeed、FSDP、Megatron、vLLM、SGLang 和 Ray。它们非常重要，但单独拿出来通常不是一套完整的后训练流水线。

本文所说的“部署后训练方法”，指的是把训练任务真正跑起来，而不是将训练完成的模型部署成 API 服务。

先理解：一个框架究竟替我们做了什么

SFT 和 DPO 比较像普通的有监督训练：读入固定数据，前向计算损失，反向传播并更新参数。PPO、GRPO 和 OPD 则多出了一条在线数据生产线：

在线训练难就难在，这几部分的计算特征不同：训练需要保存梯度，生成需要尽量大的批量和 KV Cache，奖励模型只负责打分，PPO 还可能有参考模型与价值模型。成熟框架的价值不只在于“写好了损失函数”，更在于它能组织这些角色、分配 GPU、同步参数、恢复检查点，并记录完整实验。

Hugging Face TRL 支持 支持 支持，接口仍在演进 支持 支持在线蒸馏 Trainer 学习原理、快速原型、单机实验
LLaMA-Factory 支持 支持 版本相关 版本相关 非主要方向 中文用户、WebUI、低代码微调
Axolotl 支持 支持多种偏好目标 非主要方向 支持 非主要方向 用 YAML 管理可复现实验

这里最需要注意的是：“框架里出现了某个算法名”不等于它在所有版本、模型和并行策略下都同样成熟。 尤其是在线 RL，模型架构、推理后端、LoRA、长序列与多节点组合后，支持范围会明显缩小。正式开跑前一定要用自己的目标版本查官方示例。

1. TRL：最适合把公式翻译成代码

TRL 是 Hugging Face 生态中的后训练库，直接衔接 Transformers、Datasets、PEFT 和 Accelerate。它最大的优点是抽象直观：不同算法通常对应一个 Trainer，数据处理和训练循环仍然保持 Hugging Face 用户熟悉的样子。

代码很短，但真正的效果主要取决于提示模板、生成数量、奖励是否可靠、KL 约束以及有效 batch size。Trainer 只是把循环搭好了，并不会自动替我们设计出好奖励。

TRL 目前还提供面向在线知识蒸馏的 DistillationTrainer，可将学生自己的 rollout 送给教师计算 token 分布，再以蒸馏散度更新学生。它很适合验证 OPD 思路；如果需要把超大教师、学生和推理服务拆到多节点上，NeMo RL 等分布式方案通常更合适。

**适合谁：**第一次实现某个算法、希望代码可读、模型规模不太大，或者要快速修改损失和奖励函数的人。它也是理解论文公式如何变成训练循环的最佳起点之一。

2. LLaMA-Factory：先用配置把训练跑通

LLaMA-Factory 把模型加载、数据模板、量化、LoRA、训练、评估和导出组织成统一命令，并提供 WebUI。对不想从 Trainer 代码开始搭环境的用户，它的体验很友好。

还要留意版本差异：经典文档涵盖 SFT、奖励模型、PPO、DPO 等路线，而当前新版文档的稳定范围可能有所调整。应以安装版本的对应文档和示例配置为准，不要拿旧教程中的参数直接运行新版本。

**适合谁：**希望尽快跑通 SFT/DPO、偏好中文文档和 WebUI、主要使用主流开源模型及 LoRA 的用户。

3. Axolotl：训练配置就是实验说明书

Axolotl 同样以 YAML 为中心，但更强调训练配置的可复现性和可扩展性。它支持全参数训练、LoRA/QLoRA、FSDP、DeepSpeed，以及 SFT、奖励模型、DPO、IPO、KTO、ORPO、SimPO 和 GRPO 等训练方式。

可以把它理解为：研究者把一次训练的模型、数据、采样、优化器、并行和日志设置都写进配置文件，然后用一条命令启动。这样比散落在多个 Python 脚本中的参数更容易复查，也方便在集群上批量管理实验。

Axolotl 的 GRPO 文档 还提供异步生成、流式奖励计算和重要性修正等工程能力。它位于“易用配置框架”和“在线 RL 系统”之间：比纯 Trainer 更完整，又没有把用户直接推入复杂的多角色调度系统。

**适合谁：**习惯 YAML、重视实验复现，需要稳定进行 SFT、偏好优化，并准备逐步尝试 GRPO 的团队。

4. ms-swift：Qwen 和多模态训练的实用型全家桶

ms-swift 是 ModelScope 生态的训练工具箱，覆盖大量文本模型和多模态模型。它支持 CPT、SFT、DPO、KTO、ORPO、SimPO、奖励模型训练，以及 GRPO、DAPO、GSPO、RLOO 等在线强化学习路线，并可连接 vLLM、SGLang、LMDeploy 等推理后端。

它的突出特点是模型覆盖广、中文资料多、对 Qwen 系列和多模态任务跟进快，同时把训练、评估、量化和推理放进了一套 CLI 中。对于国内常见的机器环境和模型来源，这种“一套工具走完整流程”的体验很实用。

在线 RL 功能发展很快，也意味着参数和入口可能随版本变化。工程上最好固定 Git 提交或发行版本，把官方 recipe 复制到自己的实验目录，再做小改动，而不是长期依赖一条不断变化的 main 分支命令。

**适合谁：**主要训练 Qwen、视觉语言模型或希望使用中文生态，并希望一套 CLI 同时覆盖训练和推理的用户。

5. OpenRLHF：为 PPO、GRPO 的多角色系统而生

到 PPO 阶段，一次更新可能同时涉及 Actor、Reference、Reward 和 Critic 四类模型。若每个模型都不小，怎样把它们放到不同 GPU、怎样让 Actor 用 vLLM 高速采样、怎样将新权重广播到 rollout worker，就成了主要矛盾。

与 TRL 相比，OpenRLHF 的启动命令和资源参数更多，排查问题也需要理解 Ray、DeepSpeed 和 vLLM。但当训练真正扩展到多机多卡时，这些复杂度本来就存在，框架只是把它们显式管理起来。

**适合谁：**已经验证过奖励和超参数，接下来要提高 PPO/GRPO 吞吐、扩展到多 GPU 或多节点的团队。

6. verl：把复杂 RL 数据流写成可组合系统

verl 来自字节跳动 Seed 团队，重点是大语言模型的规模化强化学习。它的 HybridFlow 抽象允许用户描述“先生成、再打分、再计算优势、最后更新”的数据流，同时由系统处理模型角色与分布式执行。

verl 对 PPO、GRPO 等算法提供现成 recipe，也方便替换奖励函数、采样器和优势估计方法。相比只把算法包装成一个 Trainer，它更像一个 RL 实验平台：研究者可以保留高性能的底层执行，同时修改上层数据流。

这类灵活性也提高了学习门槛。第一次做 SFT 或 DPO 时使用 verl 并没有明显必要；当问题变成自定义 agent rollout、多轮工具调用、不同 reward manager，或者需要在大量 GPU 上比较多种 RL 变体时，它的价值才会充分体现。

**适合谁：**准备长期开展在线 RL 研究、需要修改训练数据流，并且已经具备分布式训练经验的团队。

7. NeMo RL：覆盖最完整，尤其适合 OPD

NVIDIA NeMo RL 是面向大规模后训练的完整框架。官方算法文档覆盖 SFT、DPO、奖励模型、PPO、GRPO 及其变体，以及 OPD/MOPD。训练后端可选择 PyTorch DTensor 或 Megatron，并面向 Slurm、Kubernetes 和多节点 GPU 集群提供运行方案。

对于 OPD，它的优势尤其明显。在线蒸馏需要学生生成、教师计算 logits、按 token 计算蒸馏损失，还可能需要张量并行和跨节点传输。小实验在 TRL 中就能完成，但大模型教师加大模型学生很快会变成系统问题，NeMo RL 正是在解决这一级别的资源编排。

它的代价也很明确：配置体系、NVIDIA 软件栈和集群运维都更重。如果只有一两张消费级显卡，为了跑一次 LoRA-SFT 而引入整套 NeMo RL，通常得不偿失。

**适合谁：**NVIDIA GPU 集群用户、需要统一覆盖多种在线算法，尤其准备进行大规模 OPD 或多节点 RL 的团队。

8. slime 与 AReaL：值得关注的进阶方案

还有两套正在快速发展的框架值得关注：

  • slime 将 SGLang、Megatron 和 Ray 组合起来，强调高性能 rollout、灵活奖励、多轮工具调用与智能体训练；
  • AReaL 重点研究异步强化学习，支持 PPO、GRPO、DAPO、GSPO、RLOO 等算法，并处理异步 rollout 带来的策略陈旧问题。

它们已经具备严肃的大规模训练能力，但迭代速度快、系统概念多。对初学者来说，先用 TRL 或配置型框架确认数据与奖励正确，再进入这类系统，调试成本会低很多。

不要混淆训练框架与底层组件

很多教程会同时出现十几个项目名。它们之间通常不是互相替代，而是上下层关系：

组件 主要职责 能否单独完成后训练
Transformers 模型结构、权重加载、基础训练 API 可做简单训练，但在线 RL 需大量自建代码
PEFT LoRA、QLoRA 等参数高效微调 不能，它只决定哪些参数被训练
DeepSpeed / FSDP / Megatron 切分参数、梯度和优化器，进行分布式训练 不能，它们不是完整的算法流水线
vLLM / SGLang 高吞吐生成 rollout 或部署推理服务 不能，它们不负责完整反向训练
Ray 跨进程、跨节点调度不同模型角色 不能，它不定义 SFT/GRPO 损失
TRL / OpenRLHF / verl 等 实现算法并组织上述组件 可以

vLLM 的 RLHF 集成文档列出了它可接入的训练框架，这恰好说明了它的定位：它往往是在线训练中的“生成发动机”，而不是整辆车。

各方法落地时，代码真正需要准备什么

SFT：重点是数据模板和标签掩码

最常见的数据是一组 messages，或 prompt + completion。需要确认框架使用了与模型匹配的 chat template，并且只对需要学习的回答 token 计算损失。模板错了，模型会学到奇怪的角色标记；掩码错了，用户问题也会被当成目标答案训练。

DPO：重点是成对数据和参考策略

每条数据通常包含 prompt、chosen 和 rejected。两个回答应针对同一个提示，长度和风格偏差不能成为伪标签。还要确认参考模型是单独加载、由初始策略隐式生成，还是开启 reference-free 变体，这会直接影响显存和损失含义。

PPO：重点是四个模型的资源分配

除了提示词和奖励，PPO 还要处理 Actor、Critic、Reference 和 Reward Model。代码本身未必最难，难的是这些模型的显存、推理批量、训练批量、KL 系数和参数同步。小规模教学可从 TRL 开始，严肃扩展通常更适合 OpenRLHF、verl 或 NeMo RL。

GRPO：重点是可靠且高吞吐的奖励

GRPO 省去了 Critic，但同一提示需要生成一组回答。训练吞吐通常受 rollout 限制，因此 vLLM/SGLang 集成很重要。数学答案、代码测试和格式检查可以写成规则奖励；主观写作质量若只靠脆弱规则评分，很容易产生 reward hacking。

OPD：重点是能否拿到教师的 token 分布

普通教师 API 往往只返回文本，最多返回有限的 top-k log probability；严格的 OPD 通常需要更完整的逐 token 教师分布。还要处理教师与学生 tokenizer 是否一致、词表怎样对齐，以及教师前向的巨大计算成本。能拿到教师本地权重时，TRL 可用于原型；大规模场景优先考察 NeMo RL。

一套实际可用的选型顺序

如果没有历史包袱，可以按下面的顺序选：

  1. 先判断是不是在线训练。 SFT、DPO 优先看 TRL、LLaMA-Factory、Axolotl、ms-swift；PPO、GRPO、OPD 再考虑在线 RL 系统。
  2. 先做最小闭环。 用小模型和几百条数据确认数据格式、损失下降、生成结果与奖励方向都正确。
  3. 再根据规模换框架。 单机能跑通不代表必须永远留在单机框架；反过来，也不必一开始就引入 Ray 和多节点调度。
  4. 把推理吞吐单独估算。 在线 RL 经常不是训练慢，而是生成一批回答花费了大部分时间。
  5. 固定版本和 recipe。 记录框架、Transformers、CUDA、推理后端版本及完整配置，避免三个月后无法复现。

粗略地说：

  • **单卡学习与原型：**TRL；想少写代码则选 LLaMA-Factory；
  • **单机多卡、配置驱动：**Axolotl 或 ms-swift；
  • **多机 PPO/GRPO：**OpenRLHF 或 verl；
  • **NVIDIA 大集群与 OPD：**NeMo RL；
  • **异步 RL、复杂 agent rollout：**进一步考察 AReaL 或 slime。

这里没有永远正确的“最强框架”。真正可靠的选择，是用算法需求、模型规模、硬件环境和团队愿意维护的复杂度共同决定。

不要因为某个框架支持 GRPO，就立刻把已有的 SFT 流水线全部改成 GRPO。比较稳妥的后训练路线通常是：
