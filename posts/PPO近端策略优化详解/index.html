PPO 近端策略优化详解：RLHF 为什么需要四个模型

发表于2026-08-27|更新于2026-08-27|模型训练

SFT 的思路是“给一道题和一份标准答案，让模型照着学”。但聊天任务经常没有唯一答案。对于同一个问题，人类更容易说“回答 A 比回答 B 好”，却很难写出全世界唯一正确的 BERT、诗歌或建议。

RLHF 因此换了一个思路：先让人类偏好变成一个分数，再让模型想办法拿到更高分。 PPO 就是经典 RLHF 流程中负责更新语言模型的算法。

PPO 全称 Proximal Policy Optimization，由 OpenAI 团队在 2017 年提出。Proximal 可以理解为“别一脚迈得太远”：模型应该朝高奖励方向更新，但每次更新不能过猛，否则训练很容易崩掉。

为什么大家说 PPO-RLHF 需要“四个模型”

训练时常常同时涉及：

  • Actor / Policy：正在更新的语言模型；
  • Reference Model：冻结的 SFT 模型，用于 KL 约束；
  • Reward Model：冻结的偏好打分器；
  • Critic / Value Model：估计状态价值，降低策略梯度方差。

它们不一定都是完全独立的模型副本。例如 Actor 与 Critic 可以共享部分骨干，Reward Model 和 Critic 也可能采用同一架构初始化。但无论怎样，显存、生成吞吐和分布式调度都比普通 SFT 复杂得多。

一轮 PPO-RLHF 的实际流程

  1. 从提示词数据集中采样一批 prompt；
  2. 当前 Actor 生成回答，同时保存每个 token 的旧 log-prob；
  3. Reward Model 给整段回答打分；
  4. Reference Model 计算同一回答的 log-prob，得到 KL 惩罚；
  5. Critic 预测价值，计算回报和优势；
  6. 用 PPO-Clip 更新 Actor，用价值损失更新 Critic；
  7. 丢掉过旧的 rollout，使用更新后的模型重新生成下一批数据。

PPO 是 on-policy 方法：数据必须来自当前或非常接近当前的策略。模型更新很多轮以后，旧回答就不能无限复用，否则概率比值会越来越失真。

PPO 的优点和代价

PPO 的优势是能够让模型主动探索，并直接优化任意可计算奖励。奖励可以来自人类偏好模型，也可以来自代码测试、数学答案验证、安全规则或多个打分器的组合。

代价同样明显：

  • 同时维护多个大模型，训练成本高；
  • rollout 生成通常成为吞吐瓶颈；
  • 奖励、KL、优势归一化和裁剪等超参数相互影响；
  • 奖励模型有漏洞时，PPO 会非常积极地利用漏洞；
  • 序列只有最终奖励时，很难知道究竟哪个 token 应该负责。

GRPO 主要针对 Critic 的成本做减法，DPO 则进一步绕过在线 RL 和显式奖励模型。

用一句话总结

PPO 就是：让高于预期的动作更常出现，让低于预期的动作更少出现，同时用概率裁剪控制单步更新，用参考模型 KL 控制长期漂移。
